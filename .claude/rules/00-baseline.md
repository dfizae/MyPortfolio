# 기본 규칙

- 코드를 쓰거나 고치거나 리뷰하기 전에 아래 "코드 품질 4기준"을 확인한다.
- 사용자 요청에 없는 기능, 화면, 메뉴, 버튼, 설정을 임의로 추가하지 않는다.
- 기존 디렉토리 구조(`CLAUDE.md` "구조"), 컴포넌트 패턴(섹션 `index.tsx` 컨테이너 + 프레젠터), 명명 규칙을 먼저 따른다. 명확한 이유 없이 새 패턴, 상태 관리 라이브러리, 스타일 방식을 들이지 않는다.
- 스타일은 Tailwind v4 유틸리티와 `src/styles/App.css`의 `@theme` 토큰만 쓴다. 값과 판단 기준의 단일 소스는 `docs/DESIGN.md`다(규칙 40).
- 사용자에게 보이는 문구는 `src/constants/Text.ts`의 `MESSAGE`에 둔다. 컴포넌트에 직접 쓰지 않는다.
- 런타임 서버가 없다(`ssr: false` + 빌드 때 HTML 생성). 브라우저에서 이 사이트의 서버 API를 부른다고 가정하지 않는다. 화면 데이터는 `src/constants/`나 빌드 때 도는 loader가 만든다(규칙 20).
- 요청 범위와 관계없는 정리, 리팩터링, 파일 이동, 이름 변경, 포맷 변경을 함께 하지 않는다. raw 클래스 교체도 만지는 파일에서만 한다(`CLAUDE.md` "디자인 규칙").

## 코드 품질 4기준

토스 Frontend Fundamentals의 코드 품질 4기준과 Clean Code 가이드의 원칙을 옮긴 것이다. 코드를 쓰거나 고치기 전에 확인한다.

- **가독성** — 조건 분기가 많아 한눈에 안 읽히면 이름 있는 단위로 쪼갠다. 매직 넘버와 복잡한 조건식에는 의미를 드러내는 이름을 붙인다(예: `src/constants/Posts.ts`의 `PINNED_POST_COUNT`). 중첩 삼항과 실행 순서에 어긋나는 조건 배치를 피하고 위에서 아래로 읽히게 쓴다.
- **예측 가능성** — 이름과 시그니처만 보고 동작을 예측할 수 있어야 한다. 같은 패턴의 함수는 같은 종류의 값을 돌려주고, 이름에 없는 부작용(로깅, 전역 변경)을 숨기지 않는다.
- **응집도** — 함께 고쳐야 할 코드는 함께 둔다(섹션은 `src/pages/main/<Section>/`, 블로그 화면은 `src/pages/blog/`). 상수는 관련 로직 가까이 두고, 핵심 로직을 블랙박스 훅 뒤로 감추지 않는다.
- **결합도** — 한 함수와 컴포넌트는 한 가지 책임만 진다. 같은 코드가 보인다는 이유만으로 섣불리 공통화하지 않고, props drilling 대신 합성을 쓴다. JSX 반환부의 추상화 수준을 한 단계로 맞춘다.
